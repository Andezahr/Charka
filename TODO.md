## 1. Главный принцип: несколько игровых систем

Charka — менеджер для **разных** НРИ. Cyberpunk 2020 — первая система, D&D 5e — следующая.
Поэтому каждая новая вещь сначала проходит вопрос: **«это ядро или правила конкретной системы?»**

| Ядро [CORE] — одинаково везде | Система — свои правила |
|---|---|
| Кампания, персонаж, NPC, игровое время, хроника | Какие счётчики есть у персонажа (ХП CP2020 ≠ ХП D&D) |
| Механизм счётчиков (стратегии, attributes, контекст) | Статы, их список и производные |
| Броски кубиков: разбор `NdM+K`, лог бросков | Как устроена проверка (1d10+STAT+SKILL vs DC / 1d20+мод vs DC), что такое крит и провал |
| Механизм навыков: определение + значение у персонажа | Список навыков и их статы, стоимость развития |
| Инвентарь, предмет, тип предмета с набором свойств | Типы предметов и их поля (оружие CP2020: WA/ROF/надёжность; D&D: кубик урона, свойства) |
| Деньги — журнал операций | Валюта и её формат (эдди / зм-см-мм) |
| Боевой трекер: участники, порядок, раунды | Формула инициативы, что такое атака и урон |
| Хук «прошло N дней» | Что происходит со временем (лечение, траты, восстановление ячеек) |
| Заметки, категории, экспорт/импорт | — |

Правила:
- Код системы лежит в своём пакете (`...cp2020`, `...dnd5e`), ядро не импортирует его напрямую —
  только через интерфейсы ядра и реестр систем.
- **Кампания имеет систему** (`Campaign.system`), персонаж наследует её. UI и формы показывают только то,
  что разрешено системой кампании (например, тип счётчика `CP2020_HEALTH` нельзя создать в кампании D&D).
- Универсальные вещи (простой счётчик, заметки, деньги, кубики) доступны в любой системе.
- Числа и таблицы правил — в классах `*Rules` системы (как `Cp2020Rules`), без состояния, с юнит-тестами.
- Если сомневаешься, куда положить, — делай точку расширения в ядре и реализацию в системе.

## 2. Целевая архитектура систем (ориентир для задач ниже)

```
app.charka
 ├─ system/                      [CORE] реестр и контракт системы
 │   ├─ GameSystem               интерфейс: code ("CP2020"), displayName, currency, defaultCounterTypes,
 │   │                           itemTypes, skillCatalog, checkResolver, initiative, onTimePassed(...)
 │   ├─ GameSystemRegistry       собирает бины GameSystem в Map по code (как CounterStrategyFactory)
 │   └─ UniversalSystem          "GENERIC" — без спец-правил, только ядро
 ├─ system/cp2020/               [CP2020] Cp2020System + Rules, навыки, оружие, фамблы
 │   (стратегии счётчиков CP2020 уже здесь — S-07)
 └─ system/dnd5e/                [DND5E] позже
```

- `CounterStrategy` получает `default Set<String> getSystems()` — пустой набор = универсальная стратегия.
  `CounterStrategyFactory.getStrategiesFor(systemCode)` фильтрует для формы создания и для `CounterService.create`.
- `GameSystem.getDefaultCounterTypes()` — счётчики, создаваемые вместе с новым персонажем
  (для CP2020: STATS, ARMOR, HEALTH, REP, IP; для GENERIC — ничего).
- `GameSystem.onTimePassed(campaign, days)` вызывается из `CampaignTimelineService.proceedDate`
  вместо прямого вызова `healthCounterService.healOverTime` (лечение CP2020 становится частью Cp2020System).
- Предметы: `Item.type` (код типа) + `Item.properties` (`Map<String,String>`, таблица `item_property`).
  Тип предмета описывает система: `ItemTypeDefinition` (code, displayName, поля с типами и подписями,
  шаблон карточки/полей формы) — тот же подход, что у стратегий счётчиков. Универсальный тип `GENERIC`.
- Навыки: ядро хранит `CharacterSkill(character, skillCode, level, customName)`;
  список навыков и их статов отдаёт `GameSystem.getSkillCatalog()`.
- Проверки: `CheckResolver` системы получает `CheckRequest` (персонаж, навык/стат, DC, модификаторы)
  и возвращает `CheckResult` с шагами (как `HealthEvent`) — для единообразного UI «пошаговый расчёт».
