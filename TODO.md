## 1. Главный принцип: несколько игровых систем

Charka — менеджер для **разных** НРИ. Cyberpunk 2020 — первая система, D&D 5e — следующая.
Поэтому каждая новая вещь сначала проходит вопрос: **«это ядро или правила конкретной системы?»**

| Ядро [CORE] — одинаково везде | Система — свои правила |
|---|---|
| Кампания, персонаж, NPC, игровое время, хроника | Какие счётчики есть у персонажа (ХП CP2020 ≠ ХП D&D) |
| Механизм счётчиков (стратегии, attributes, контекст) | Статы, их список и производные |
| Броски кубиков: разбор `NdM+K`, лог бросков | Как устроена проверка (1d10+STAT+SKILL vs DC / 1d20+мод vs DC), что такое крит и провал |
| Механизм навыков: определение + значение у персонажа | Список навыков и их статы, стоимость развития |
| Инвентарь, предмет, тип предмета с набором свойств | Типы предметов и их поля (оружие CP2020: WA/ROF/надёжность; D&D: кубик урона, свойства) |
| Деньги — журнал операций | Валюта и её формат (эдди / зм-см-мм) |
| Боевой трекер: участники, порядок, раунды | Формула инициативы, что такое атака и урон |
| Хук «прошло N дней» | Что происходит со временем (лечение, траты, восстановление ячеек) |
| Заметки, категории, экспорт/импорт | — |

Правила:
- Код системы лежит в своём пакете (`...cp2020`, `...dnd5e`), ядро не импортирует его напрямую —
  только через интерфейсы ядра и реестр систем.
- **Кампания имеет систему** (`Campaign.system`), персонаж наследует её. UI и формы показывают только то,
  что разрешено системой кампании (например, тип счётчика `CP2020_HEALTH` нельзя создать в кампании D&D).
- Универсальные вещи (простой счётчик, заметки, деньги, кубики) доступны в любой системе.
- Числа и таблицы правил — в классах `*Rules` системы (как `Cp2020Rules`), без состояния, с юнит-тестами.
- Если сомневаешься, куда положить, — делай точку расширения в ядре и реализацию в системе.

## 2. Целевая архитектура систем (ориентир для задач ниже)

```
app.charka
 ├─ system/                      [CORE] реестр и контракт системы
 │   ├─ GameSystem               интерфейс: code ("CP2020"), displayName, currency, defaultCounterTypes,
 │   │                           itemTypes, skillCatalog, checkResolver, initiative, onTimePassed(...)
 │   ├─ GameSystemRegistry       собирает бины GameSystem в Map по code (как CounterStrategyFactory)
 │   └─ UniversalSystem          "GENERIC" — без спец-правил, только ядро
 ├─ system/cp2020/               [CP2020] Cp2020System + Rules, навыки, оружие, фамблы
 │   (стратегии счётчиков CP2020 уже здесь — S-07)
 └─ system/dnd5e/                [DND5E] позже
```

- `CounterStrategy` получает `default Set<String> getSystems()` — пустой набор = универсальная стратегия.
  `CounterStrategyFactory.getStrategiesFor(systemCode)` фильтрует для формы создания и для `CounterService.create`.
- `GameSystem.getDefaultCounterTypes()` — счётчики, создаваемые вместе с новым персонажем
  (для CP2020: STATS, ARMOR, HEALTH, REP, IP; для GENERIC — ничего).
- `GameSystem.onTimePassed(campaign, days)` вызывается из `CampaignTimelineService.proceedDate`
  вместо прямого вызова `healthCounterService.healOverTime` (лечение CP2020 становится частью Cp2020System).
- Предметы: `Item.type` (код типа) + `Item.properties` (`Map<String,String>`, таблица `item_property`).
  Тип предмета описывает система: `ItemTypeDefinition` (code, displayName, поля с типами и подписями,
  шаблон карточки/полей формы) — тот же подход, что у стратегий счётчиков. Универсальный тип `GENERIC`.
- Навыки: ядро хранит `CharacterSkill(character, skillCode, level, customName)`;
  список навыков и их статов отдаёт `GameSystem.getSkillCatalog()`.
- Проверки: `CheckResolver` системы получает `CheckRequest` (персонаж, навык/стат, DC, модификаторы)
  и возвращает `CheckResult` с шагами (как `HealthEvent`) — для единообразного UI «пошаговый расчёт».

### Домашние правила (хоумбрю)

Правила, которых нет в книгах или которые мы дополнили сами. **В коде помечены `HOMEBREW`** (поиск по этому слову), в справочнике — словом «Хоумбрю». Менять можно свободно; правила из книг так не помечаются.

| Что решили | Где менять | Почему так |
|---|---|---|
| Стандартный запасной магазин стоит по ставке расширенного (безгильзовые 0.5 eb, с гильзой 1 eb за патрон) | `Cp2020MagazineRules.price` | В книгах цены стандартного магазина нет |
| Цена — за всю вместимость, а не только за прибавку; дробная — вверх | `Cp2020MagazineRules.price` | Solo of Fortune II говорит «за патрон», цена в eb целая |
| Магазин для тяжёлого оружия — 2 eb за патрон | `Cp2020MagazineRules.Rate.HEAVY` | В книге 2–3 eb на усмотрение мастера, взята нижняя граница |
| Магазин меньше стандартного не подходит | `Cp2020MagazineRules.fits` | Книга описывает только расширение |
| Размеры в справочнике: стандартный, ×2, ×5 (в форме предмета — любой) | `Cp2020MagazineRules.CATALOG_EXTENSIONS` | Чтобы не перечислять все размеры |
| Без магазина заряжаются револьверы, дерринджер, Winchester M70, лук, арбалет, огнемёт | `directLoad` в `Cp2020Weapons` | Книга прямо не делит оружие на такие группы |

| Оружие из справочника продаётся с полным стандартным магазином | `Cp2020Weapons.gun` | Книга молчит |
| Заправка огнемёта — 10 выстрелов | `Cp2020Ammo` | В книге числа нет, взят магазин F-253 |

## 5. Журнал решений

Сюда — короткие записи о принятых решениях, чтобы не обсуждать их заново.

- 2026-10-29 — Мультисистемность: у кампании есть система, правила систем изолированы в своих пакетах,
  ядро общается с ними через `GameSystem` и реестры (см. разделы 1–2).
- 2026-10-29 — Порядок: фундамент → ядро систем → кубики → навыки → оружие → бой → развитие → редкое.
  Новые правила CP2020 не пишутся до задач S-01..S-03, чтобы не переделывать.
- 2026-10-29 — Хранилище — PostgreSQL (не H2-файл); 2026-10-30 — в Docker (`compose.yaml`, порт 5433), а не установленный в системе PG. Схема только через Flyway (`ddl-auto=validate`), каждое изменение
  сущностей — новая миграция `V<n>__*.sql`. SQL пишем переносимым: тесты гоняют те же миграции на H2 в режиме PostgreSQL
  (Testcontainers — если понадобятся PG-специфичные вещи).
- 2026-10-29 — Ошибки страниц: `IllegalArgumentException` = 400, `*NotFoundException` (`NoSuchElementException`) = 404.
  Код «не найдено» бросает `NotFoundException.forId("Entity", id)` (2026-10-30: один общий класс вместо класса на сущность).
- 2026-10-30 — Новая `Campaign` по умолчанию GENERIC (существующие в БД мигрированы в CP2020). Персонаж без кампании — GENERIC.
  Код системы персонажа вычисляет статический `GameSystemRegistry.systemCodeOf`, чтобы `CounterService` не зависел
  от реестра (иначе цикл: реестр → `Cp2020System` → `HealthCounterService` → `CounterService`).
- 2026-10-30 — Проверки: успех при «итог ≥ сложность» (CP2020 и GENERIC). Фамбл CP2020 — всегда провал, последствия —
  таблица фамблов (K-06). Резолверы без состояния, `DiceRoller` им передаёт `CheckService`.
- 2026-10-30 — Роли/классы — коллекция ядра `Character.roles`, список даёт система; ролей может быть несколько, уровень роли = уровень
  спецспособности. Навыки: каталог в коде системы, в БД только коды и уровни;
  ядро получает текущие статы через `GameSystem.getCurrentStats`, поэтому не знает о счётчиках CP2020.
- 2026-10-30 — Домашние правила автора важнее книги: новая роль открывается на 4 уровне спецспособности текущей (из Cyberpunk RED, K-11). Такие правила помечаем в коде как домашние, в K-08 они не сверяются.
- 2026-10-30 — Источник правил CP2020 — PDF книги в корне проекта (в `.gitignore`, не публикуем). Значения задач «сверить» берём оттуда, а не по памяти; чего в книге нет, помечаем как наше решение.
- 2026-10-30 — Игромеханика без обходных путей: действие, которого нет по правилам или в интерфейсе, не должно держаться на побочном эффекте (например, смене роли туда-обратно). Сервер сам проверяет правила, а не только скрывает кнопку.
